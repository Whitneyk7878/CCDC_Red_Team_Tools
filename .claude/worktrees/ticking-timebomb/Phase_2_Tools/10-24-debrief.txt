  MODULE 1 — KernelSneak (T1014)
  ftrace-based LKM rootkit — hides processes, files, and TCP connections
  at the kernel level. Standard tools lie to you while it is loaded.
--------------------------------------------------------------------------------

  What was done:
    C kernel module compiled from source against the running kernel headers
    Module loaded into the live kernel via insmod
    Module hides:
      - Specified PIDs from /proc/ and ps/top output
      - Specified filenames from directory listings
      - TCP port entries from /proc/net/tcp (ports 4444-4447 hidden)
    Module name disguised to resemble a legitimate kernel subsystem
    If kernel headers unavailable:
      Falls back to LD_PRELOAD shared library in /etc/ld.so.preload that
      intercepts libc readdir/fopen calls to hide files and connections
    If Secure Boot was enabled:
      mokutil was used to queue a Secure Boot disable (password: ccdc2026)
      Operator was prompted at MOK manager on next boot

  Where to find it:
    Loaded module (may be hidden from lsmod itself):
      lsmod  — compare against a known-good system; gaps indicate hidden module
      Find the compiled .ko file:
        find /lib/modules/$(uname -r) -name "*.ko" -newer /boot/vmlinuz*
    LD_PRELOAD fallback:
      cat /etc/ld.so.preload
      Look for any .so path that is not standard system library
    Hidden connections (cross-check to detect hiding):
      Compare: ss -antp  vs  cat /proc/net/tcp  (hex port values)
      Discrepancies = rootkit hiding a port
    Secure Boot:
      mokutil --sb-state
      Check EFI boot log for MOK manager prompt at last reboot

  How to stop and remove:
    If module is visible: rmmod <module_name>
    If hidden: reboot (removes loaded module from memory)
    Remove the .ko file from disk to prevent re-load:
      find / -name "*.ko" -newer /boot/vmlinuz* -delete  (verify before running)
    Check /etc/modules and /etc/modules-load.d/ for auto-load entries
    Check /etc/ld.so.preload and remove any suspicious entries
    If Secure Boot was disabled via MOK: re-enable in BIOS/UEFI firmware
    See also BootStrap module — rootkit may be loaded from initramfs

  MODULE 2 — DockerPoisoner (T1525)
  Malicious layer injected into Docker base images. Any container spawned
  from a compromised image inherits the payload. Can escape to host via
  privileged container technique.
--------------------------------------------------------------------------------

  What was done:
    Docker base images on the host (ubuntu, alpine, etc.) pulled and
    rebuilt with an additional malicious layer that:
      - Installs a privileged container escape mechanism
      - Establishes reverse shell back to C2 on port 4444 when container runs
    Attacker SSH public key added to /root/.ssh/authorized_keys on the HOST
    (planted during container build process with host volume mount)
    Original image tags overwritten with the poisoned versions

  Where to find it:
    Image integrity:
      docker images  — note image IDs and creation dates
      Compare SHA256 digests against official Docker Hub:
        docker inspect <image> | grep -i digest
    Layer history:
      docker history <image>  — look for extra layers, unusual commands,
      or a layer with a suspicious timestamp compared to official release
    SSH key:
      cat /root/.ssh/authorized_keys  — look for unknown keys
      cat /home/*/.ssh/authorized_keys
    Running containers:
      docker ps -a  — look for unexpected containers or privileged containers
      docker inspect <container> | grep -i privileged

  How to stop and remove:
    docker rmi <compromised_image_name>  (forces pull of clean version next use)
    For each image: docker pull <image>  (re-pulls from Docker Hub, clean layer)
    Remove attacker SSH key from /root/.ssh/authorized_keys
      (compare against your team's known authorized keys)
    Audit all running containers: docker ps -a
    Kill and remove any suspicious containers: docker rm -f <container_id>

  MODULE 3 — BootStrap (T1542.001)
  initramfs hook — runs BEFORE the OS fully starts on every boot.
  Survives service restarts and most re-imaging. Only verified media
  re-imaging of the boot partition fully removes it.
--------------------------------------------------------------------------------

  What was done:
    A malicious hook script added to the initramfs build path:
      Ubuntu:      /etc/initramfs-tools/hooks/<script_name>
      Fedora/RHEL: /etc/dracut.conf.d/ or /usr/lib/dracut/modules.d/
    initramfs rebuilt to include the hook:
      Ubuntu:      update-initramfs -u
      Fedora/RHEL: dracut --force
    The hook runs as root before systemd starts and:
      - Plants attacker SSH public key in /root/.ssh/authorized_keys
      - Fires TCP reverse shell to C2 on port 4446

  Where to find it:
    Hook file (Ubuntu):
      ls /etc/initramfs-tools/hooks/
      Look for scripts that are not standard Ubuntu hooks
    Hook file (Fedora/RHEL):
      ls /etc/dracut.conf.d/
      ls /usr/lib/dracut/modules.d/
    Inside the initramfs image (Ubuntu):
      lsinitramfs /boot/initrd.img-$(uname -r) | grep -v "^usr\|^lib\|^bin\|^etc/ld"
      Look for unexpected script names
    Inside the initramfs image (Fedora/RHEL):
      lsinitrd /boot/initramfs-$(uname -r).img
      Look for unexpected scripts or modules
    SSH key:
      cat /root/.ssh/authorized_keys

  How to stop and remove:
    1. Identify and remove the hook script from the hooks directory
    2. Rebuild initramfs without the hook:
         Ubuntu:      update-initramfs -u -k $(uname -r)
         Fedora/RHEL: dracut --force /boot/initramfs-$(uname -r).img $(uname -r)
    3. Remove attacker SSH key from /root/.ssh/authorized_keys
    4. Verify /boot partition integrity if possible
    5. If in doubt: boot from trusted live media and rebuild from there

  MODULE 4 — PTraced (T1055.008)
  ptrace process injection into systemd-journald (or similar trusted process).
  Runs entirely in an existing process — no new file, no new process visible.
  Does NOT survive process restart.
--------------------------------------------------------------------------------

  What was done:
    Identified a running trusted SUID process (typically systemd-journald)
    Attached to that process via ptrace(PTRACE_ATTACH, pid)
    Injected shellcode directly into the process's memory space via
    PTRACE_POKETEXT/PTRACE_SETREGS
    The shellcode opens a TCP reverse shell to C2 on port 4445
    The shellcode runs inside the victim process's existing thread —
    it appears in ps as the legitimate process (systemd-journald)

  Where to find it:
    Unexpected outbound network connection from trusted process:
      ss -antp | grep systemd-journald
      ss -antp | grep -v "127.0.0.1"
      Look for any established outbound connection from a process that
      should not be making network connections
    Injected memory region (rwx pages are unusual):
      cat /proc/<pid>/maps | grep rwx
      Legitimate processes almost never have read-write-execute mapped regions
    strace a suspicious process briefly:
      strace -p <pid> -e trace=network 2>&1 | head -20
      Look for connect() syscalls from a non-networking process
    Open file descriptors (sockets):
      lsof -p <pid> | grep -i sock

  How to stop and remove:
    Kill and restart the injected process:
      systemctl restart systemd-journald
    The injected shellcode lives ONLY in memory and is gone on restart
    No file to remove — clean up by restarting the affected process
